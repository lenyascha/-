# Правило: безопасность и конфиденциальность

Читай перед ЛЮБОЙ отправкой кандидату/HR-интервьюеру и перед правкой
`fetch_submission.py`/`hh_inbox.py`/промптов `llm_client.py`.

## ✅ Чек-лист внешней отправки (кандидату / HR-интервьюеру) — проверять каждый раз

1. **Подпись — фиксированная, `templates.SIG`: «А. Терещенков».** Имя
   владельца HH-аккаунта (`GET /me`) — не выдумывать другое, не
   подставлять своё: кандидаты знают это имя с прошлой переписки, смена на
   середине диалога — красный флаг кандидату и накладка нам.
2. **Получатель сверен:** `neg_id`↔ФИО↔`resume_id` по базе. Один человек =
   одно сообщение.
3. **Текст — сначала превью**, реальная отправка только после явного
   решения (`confirmed=False` сначала везде, где есть параметр).
4. **НИКОГДА не озвучивать кандидату вилку ЗП работодателя**, не давать
   причин отказа (только `TMPL_REJECT_GENERIC`, или, при закрытии
   вакансии, `TMPL_REJECT_VACANCY_CLOSED` — единственное исключение,
   потому что там причина не секретна).
5. **После отправки — перепроверить доставку** (перечитать
   `/negotiations/{neg_id}/messages`) — у HH глюки с пустыми системными
   сообщениями, `move_with_message()` уже защищает, но факт доставки стоит
   перепроверять на важных сообщениях.

## Контекст для модели, пишущей кандидату — жёсткая изоляция

Черновик ответа кандидату (`hh_inbox.py`, `auto_reply.py`) строится ТОЛЬКО
по `Вакансии/<роль>/FAQ_кандидату.md`. **`Регламент_найма.md` в эту модель
НЕ передаётся НИКОГДА** — там потолок ЗП, возрастные отсечки,
стоп-факторы, требование по гражданству. Поверх промпта — детерминированный
фильтр `llm_client.reply_is_safe()` (режет числа ≥100 000 и слова
«потолок/вилка/бюджет/балл/категория/гражданство»): текст кандидата идёт в
модель и является потенциальной инъекцией, на «мы попросили модель не
говорить» полагаться нельзя. Не прошло фильтр → карточка уходит рекрутёру
БЕЗ черновика, не с урезанным.

Тот же принцип для суммы ЗП: `TMPL_TEST_RAC/PIIPL/ARCH` несут одну и ту же
фразу про индивидуальное обсуждение денег НЕЗАВИСИМО от того, попал
кандидат в вилку или нет — делать фразу условной по сумме нельзя, само её
наличие/отсутствие станет утечкой сигнала (см.
`.claude/rules/hiring-funnel.md`).

## fetch_submission.py — SSRF и атрибуция сбоев

Ссылку в сообщении пишет кандидат — произвольный URL оттуда это запрос,
который мы выполним от своего имени. Ходить ТОЛЬКО по allow-list хостов
(`_HOST_HANDLERS`), только публично доступное, без авторизации.

**Свой сбой и вину кандидата нельзя описывать одной строкой.** Пример
реального бага: GitHub API без токена — лимит 60 запросов/час на IP, при
исчерпании отвечает 403, неотличимо от «репозиторий приватный», если не
посмотреть заголовки (`X-RateLimit-Remaining`). Итог — заказчик получал
`decision_note` с ложным «кандидат закрыл доступ». Правило на будущее для
любого внешнего вызова в этом модуле: если сбой может быть НАШИМ (лимит,
таймаут, сеть), формулировка кандидату/заказчику обязана это отражать
явно («НАША СТОРОНА: …»), а не сворачиваться в общую фразу вида «недоступно».

## Непрочитанное не теряется молча

Условие тестового задания требует публичного доступа — значит закрытая
ссылка/нечитаемый формат это ФАКТ о кандидате, который должен быть виден
заказчику, а не тихо выпасть из оценки. Всё непрочитанное копится в
`skipped` и уходит в `decision_note`. При добавлении новой ветки разбора
формата — если формат не распознан, класть его в `skipped`, не просто
возвращать `False`/пропускать молча (реальный баг: нативные Google Docs
без расширения в имени файла проваливались бесследно, вся работа
кандидата терялась без единой записи об этом).

## text-to-SQL для свободных вопросов (`hiring_db.run_readonly_query`)

Только `SELECT`/`WITH`, фильтр на запрещённые ключевые слова. Действия
из свободного текста («отказать всем из Москвы») — только через тот же
гейт «черновик → явное подтверждение», НЕ в обход preflight-проверок
`hh_core.py` (контракты — `.claude/rules/hh-api.md`).
