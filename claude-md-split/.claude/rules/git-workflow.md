# Правило: координация нескольких чатов Claude Code

⚠ Читай это ПЕРЕД ЛЮБОЙ задачей (правкой кода) — не только когда пользователь
явно сказал «работаем параллельно». Это не опциональная справка, а гейт,
который проходишь молча, без вопроса пользователю, в начале каждой сессии в
этой папке.

## Зачем

Если в папке параллельно работают несколько чатов (в т.ч. над РАЗНЫМИ, не
связанными задачами) — не жди, пока пользователь опишет процесс. Определяй
сама, координируйся через файлы на диске, не через пересказ. Правило
постоянное, действует в ЛЮБОЙ будущей сессии, не только текущей.

## Протокол (молча, без вопроса, перед началом работы)

1. Прочитать `.tasks/` — путь ВСЕГДА абсолютный,
   `C:\Users\internet\Desktop\HRochka\.tasks\`, даже если сессия работает в
   worktree другой задачи (см. п.4).
2. Прочитать `git branch --list "task/*"` и `git worktree list`.
3. Самой придумать слаг задачи из формулировки пользователя (коротко,
   латиницей, kebab-case) — формат/имя не спрашивать.
4. Если файлы/модули задачи не пересекаются ни с одной активной записью
   `.tasks/` — завести ветку `task/<slug>` от `master` (или
   `task/<slug>/<часть>` + отдельный `git worktree` в
   `C:\Users\internet\Desktop\HRochka-worktrees\<slug>__<часть>`, если явно
   параллельная работа над ОДНОЙ задачей несколькими чатами), создать
   `.tasks/<slug>.md` по шаблону `.tasks/_TEMPLATE.md`, начать работу — без
   остановки на подтверждение (это не рискованное действие).
5. Если пересечение ЕСТЬ — с чужой активной задачей или со списком «вечно
   эксклюзивных» действий ниже — остановиться, спросить пользователя, не
   решать самой.

`.tasks/*.md` **не версионируется git** (в `.gitignore`) — живое состояние
координации между чатами сейчас, не история проекта (историю несут ветки и
коммиты). Один файл на задачу, не общий список — чтобы реестр сам не стал
источником конфликтов при параллельной записи. Тот же приём уже есть в
проекте: `data/.tg_bot2.lock` — локальный, не версионируемый файл для той
же цели (не пускать два процесса одновременно), см.
`hiring_db._acquire_singleton_lock()` в `Документация/Архитектура.md`.

## Вечно эксклюзивные действия

Сколько бы задач ни шло параллельно, выполняет только ОДИН чат в момент, и
только с подтверждением пользователя:
- реальные (не dry-run) действия на HH — отказ/приглашение/тестовое/сообщение;
- `config/.env` и обновление HH-токена (`refresh_token.py`);
- старт/остановка `tg_bot2.py`;
- публикация `Документация/Техническая_документация.html` через Artifact.

## Мерж

- Мерж частей одной задачи — тоже не параллельно: под-ветки вливаются в
  ветку задачи по одной (автоматически, без вопроса — это ещё не `master`,
  откат дёшев). Конфликты разруливаются на этом шаге, не в процессе
  работы; при реальном конфликте (не fast-forward) — не гадать, какая
  сторона верная, показать пользователю обе версии, спросить.
- Финальный мерж ветки задачи В `master` — уже НЕ автоматически, только с
  подтверждением: своего PR/ревью в проекте нет, это единственная точка
  проверки перед тем, как задача войдёт в основную линию.
- После мержа всех частей и самой ветки в `master` — закрытие задачи
  АВТОМАТИЧЕСКОЕ, без отдельного вопроса (подтверждение уже получено на
  самом мердже): удаляются `.tasks/<slug>.md`, ветка `task/<slug>`
  (`git branch -d` — сработает только если правда влита, заодно и
  проверка) и её `git worktree`, если был отдельный.

## Артефакт технической документации — обновлять ТОЛЬКО по явной просьбе

Есть опубликованный Artifact (веб-страница claude.ai) с тех.документацией
всего проекта: архитектура, карта модулей, воронка, контракты, журнал
ошибок. Правило поменялось 04.08.2026 — см.
`Документация/Журнал_решений.md` для истории вопроса.

**Текущее правило:** обновлять и переопубликовывать ТОЛЬКО когда заказчик
сам попросил («обнови документацию», «синхронизируй артефакт») — НЕ
догадываться по факту доработки, НЕ предлагать самой. Между обновлениями
документ неизбежно отстаёт от кода — ожидаемо, не баг, инициативно не
чинить.

- **URL (не менять, обновлять ТОЛЬКО через него):**
  `https://claude.ai/code/artifact/1fbb29dc-4636-452c-a03b-a64586c80df7`
- **Редактируемый исходник — в репозитории:**
  `Документация/Техническая_документация.html` = содержимое артефакта (без

⚠ Если публикация вернула «конфликт версий» — это НЕ значит, что артефакт
пропал, это защита от перезаписи чужих правок. Прочитать текущую версию
(`WebFetch` по URL — живой артефакт отдаёт реальный документ, обёрнутый в
служебный фрейм, не 404) и опубликовать заново по ТОЙ ЖЕ ссылке. Не заводить
новый адрес (реальная ошибка сессии 31.07.2026 — журнал инцидентов п.25).
