# Архитектура проекта

Справочник «как это устроено сейчас»: дерево репозитория, карта модулей, схема
БД. Не грузится автоматически в каждую сессию — читай целиком или по разделу
(`grep`/поиск по имени модуля), когда задача касается конкретного файла из
`code/`. Хронология решений («почему сделали именно так» с датами) —
`Журнал_решений.md`. Прошлые баги — `Журнал_инцидентов.md`. Обязательные
правила поведения — `.claude/rules/*.md`.

## Дерево (всё локально, без внешнего сервера)

```
config/.env          — секреты: HH-токен, (опц.) телеграм-бот
data/hiring.db        — SQLite, вся история кандидатов и решений
code/                 — весь код (hh_core.py, hiring_db.py, templates.py, ...)
Вакансии/<роль>/Регламент_найма.md — критерии и правила по каждой вакансии
Документы_HR/         — готовые шаблоны для HR-интервью (docx)
```

3 вакансии в работе — **все три равноценны, не пропускать третью**:
| role_code | Вакансия | HH vacancy_id |
|---|---|---|
| rac | Руководитель аналитического центра | 134764878 (перепубликована 01.07.2026, старый ID 132359929 в архиве) |
| piipl | Руководитель ИИ-платформы | 132370253 |
| arch | Архитектор данных и аналитических платформ | 134544725 |

## Установка и перенос на другой ПК

Тестов/линтера/сборки нет — набор автономных Python-скриптов, не пакет.
Установка одной командой — **`setup.bat` в корне** (двойной клик): ставит
пакеты, докачивает Chromium для playwright, создаёт недостающие папки,
накатывает схему `data/hiring.db`, переопределяет `PROXY_BIND_IP` под эту
машину, живыми запросами проверяет HH-токен, оба Telegram-токена и ключ
Anthropic. Отчёт по-русски, «блокеры / оговорки»; exit-код 0 = можно
запускать `run_bot.bat`.

Он же — диагностика при «что-то не работает»:
```bash
py code/setup_check.py                      # только проверить
py code/setup_check.py --install --write    # то же, что setup.bat
py code/setup_check.py --offline            # без сетевых проверок
```
`--write` чинит только безопасное (папки, схема БД, `PROXY_BIND_IP`,
`config/.env.example`). **Секреты не придумывает и не трогает.**

**Обязательно копировать при переносе** (остальное — код, в git/архиве):
- `config/.env` — единственное невосстановимое автоматически (секретный файл,
  не пересылать открытыми каналами);
- `data/hiring.db` — вся история кандидатов и решений;
- `Вакансии/**` — регламенты, FAQ, папки кандидатов (досье и дашборд
  сравнения собираются ТОЛЬКО из файлов папки кандидата, база тут не
  поможет).

После копирования: `setup.bat` → поправить, что назовёт блокером →
`run_bot.bat`. Единственная машинозависимая переменная — `PROXY_BIND_IP`
(локальный IP физического адаптера, см. `net_bind.py`); `setup_check.py`
определяет и прописывает сам.

Ручная установка, если `setup.bat` не подходит:
```bash
pip install -r code/requirements.txt   # requests, openpyxl, reportlab, pypdf, playwright, python-docx, docx2pdf
python -m playwright install chromium   # отдельный шаг: pip сам браузер не ставит
pip install faster_whisper              # только если нужна транскрибация
```
(`docx2pdf` требует установленный MS Word — им рендерится PDF чек-листа
после интервью.) Все скрипты запускаются из `code/`, сами читают
`../config/.env` и открывают `../data/hiring.db` — пути от файла модуля,
поэтому проект переносится в любую папку без правок.

## Карта модулей (code/)

Слоями, от HH API до вывода наверх. Поведенческие правила/контракты,
вытащенные из этих модулей в actionable-форму — см. `.claude/rules/`:
`hh-api.md` (hh_core/парсинг ЗП/токен), `hiring-funnel.md` (funnel/автопилот),
`telegram.md` (tg_bot2/клавиатура/outreach), `database.md` (hiring_db/схема).

- **`hh_core.py`** — тонкий клиент HH API (`get_headers`, `get_resume`,
  `change_collection`, `send_chat_message`) + ВСЕ контракты воронки поверх
  (`move_to_assessment/reject/consider/interview`, `record_test_score`,
  preflight `_preflight_reject`/`_preflight_assessment`,
  `_salary_gate_passed`). ЕДИНСТВЕННОЕ место смены состояния отклика на HH —
  не дублировать `change_collection` в других модулях. `move_with_message()`
  — обход бага HH API (пустое сообщение при смене коллекции). Контракты —
  `.claude/rules/hh-api.md`.
- **`hiring_db.py`** — весь доступ к `data/hiring.db` (sqlite3, без ORM).
  `ensure_schema()` накатывает `schema_sqlite.sql` при первом обращении.
  Поиск кандидата по имени — `LOWER()` на стороне Python (`full_name_lower`),
  НЕ FTS и НЕ SQL `LOWER()`/`LIKE` (кириллица, см. `.claude/rules/database.md`).
  `run_readonly_query()` — read-only SQL от LLM для свободных вопросов к базе
  (см. `llm_client.write_readonly_sql`/`summarize_query_result`); фильтр на
  запрещённые ключевые слова (не `SELECT`/`WITH` → отказ). `hh_core.py`
  вызывает функции модуля для записи side-effects после каждого действия на
  HH — `applications`/`activity_log` обновляются рядом с изменением на HH,
  не отдельным синком.
- **`sync_hh.py`** — забирает новые отклики/резюме с HH →
  `hiring_db.upsert_candidate_from_hh`/`upsert_application` → база.
  Однонаправленно HH→БД; обратной синхронизации нет, все исходящие — только
  через `hh_core.py`.
- **`templates.py`** — все шаблоны сообщений кандидатам (`TMPL_*`) + фикс.
  подпись `SIG`. ЕДИНСТВЕННОЕ место текста сообщений — не собирать текст
  inline в других модулях.
- **`funnel.py`** — чистая логика автопилота воронки (`next_action`,
  `run_step`): по стадии+профилю решает следующий шаг (резюме-скрининг →
  salary-gate → тест → детект сдачи). К HH обращается ТОЛЬКО из `run_step`
  при `dry_run=False` (вызывается из `tg_bot2.py`). Полное поведение,
  автоотказы, RESUME_REJECT_CATEGORY — `.claude/rules/hiring-funnel.md`.
- **`tg_bot2.py`** (самый крупный модуль, ~1500 строк) — двухрежимный
  Telegram-бот, длинный поллинг (`get_updates`/`run()`):
  1. **Командный режим** (`ADMIN_CHAT_ID`) — разбор свободного текста через
     `llm_client.classify_admin_text`, диспетчер `admin_dispatch`. Голосовые
     — тоже команды: `transcribe()` (faster_whisper) → текст → тот же путь;
     ИСКЛЮЧЕНИЕ — этап `await_voice` пост-интервью пайплайна (голосовое =
     оценка, не команда). Пайплайн стартует «собеседование с Ивановым
     завершилось» (`interview_done_start`) либо, если транскрибация встречи
     уже готова, продолжается командой «чек-лист по Иванову»
     (`checklist_from_transcript_start`). **Свободные вопросы к базе** →
     text-to-SQL: `llm_client.write_readonly_sql` →
     `hiring_db.run_readonly_query` → `llm_client.summarize_query_result` —
     ответ текстом, SQL не показывается; действия («отказать всем из
     Москвы») — только через гейт «черновик → явное подтверждение».
  2. **Стейт-машина кандидата** (`tg_scheduling`) — приглашение → слот
     Телемоста → подтверждение (`apply_transition`/`_handle_candidate`).
     Это **ПЕРВИЧНОЕ интервью** (15–20 мин, HR-интервьюер) — бот согласует
     время сам.
     ⚠ **Второй, РУЧНОЙ источник встреч — `interview_slots`, ДРУГОЙ этап:
     ВТОРОЕ, ФИНАЛЬНОЕ собеседование с Плаксиным Д.А.** HR-интервьюер
     списывается с кандидатом ЛИЧНО в Telegram, бот не участвует, в
     `tg_scheduling` такие слоты не появляются НИКОГДА. Полный поток —
     `.claude/rules/telegram.md`.
  3. Фоновый `_scheduler_loop()` — тики: `_sync_tick`, `_funnel_tick` (только
     при `AUTO_FUNNEL=1`), `_refresh_token_if_due` (раз в 5 дней), вечерний
     свод по `EVENING_SUMMARY_TIME`. Тики НИЧЕГО не показывают по своей
     инициативе, кроме сбоев и раздела «🔔 Уведомления» — детали и список
     кнопок см. `.claude/rules/telegram.md`.
  4. **`_acquire_singleton_lock()`** (`msvcrt.locking()` на
     `data/.tg_bot2.lock`) — не даёт второй копии бота на этой машине. Запуск/
     остановка — ТОЛЬКО через `run_bot.bat`/`run_bot_hidden.vbs`/
     `stop_bot.ps1`, не ручным `Stop-Process`.
  `FUNNEL_DRY_RUN=1` (по умолчанию) — карточки «бы отправил» без реальной
  отправки; `_citizenship_ok()` — стоп-фактор по гражданству, только arch.
- **`llm_client.py`** — обёртка над провайдером (`_anthropic_chat`, выбор
  через `PARSER_LLM_PROVIDER`) — разбор свободного текста кандидата/админа +
  ассистентская оценка (`parse_candidate_reply`, `parse_admin_command`,
  `assess_for_table`, `parse_checklist_voice`), плюс text-to-SQL
  (`write_readonly_sql`, `summarize_query_result`). Все вызовы к Anthropic —
  `temperature=0`. В промптах — жёсткая расшифровка сокращений вакансий
  (`rac`=РАЦ, `piipl`=РИИП, `arch`=Архитектор) и явное указание:
  `salary_currency` в базе = `'RUR'` (легаси HH.ru), НЕ `'RUB'`.
  `_anthropic_request()` — общий ретрай (до 2 повторов) при временных
  статусах (408/429/5xx/529) и сетевых исключениях; 400/401/403 НЕ
  ретраятся.
- **`test_autoscore.py`** — автооценка сданного тестового: собирает
  материалы (`fetch_submission`), отдаёт модели с ПОЛНЫМ текстом
  `Регламент_найма.md` (`llm_client.score_test_submission`), пишет результат
  ЕДИНОЙ точкой `hh_core.record_test_score`. Запуск — из
  `tg_bot2._funnel_tick` на стадии `ready_to_score`. Код НЕ переинтерпретирует
  регламент: `RUBRIC_BLOCKS`/`THRESHOLDS`/`BLOCK_MAX` — дословная перепись
  регламента (РАЦ: 5 блоков×20, A≥75·B≥55; РИИП: 7 блоков,
  `BLOCK_MAX["piipl"]=None`). Итоговый балл считает КОД
  (`_final_from_blocks` — сумма блоков), у модели не спрашивают. Категорию +
  спец-правило РИИП («блок 2 или 6 <половины») тоже код (`_category` +
  `below_half` от модели). `manual_anchors()` кладёт в промпт 2–3 РЕАЛЬНЫЕ
  ручные оценки той же роли — единственный носитель стандарта «на сколько
  тянет глубина».
- **`fetch_submission.py`** — чтение того, что кандидат приложил ссылкой.
  Ходим ТОЛЬКО по allow-list хостов (`_HOST_HANDLERS`) — SSRF-риск, см.
  `.claude/rules/safety.md`. Форматы: текст/код, `.ipynb` (base64-картинки
  выводов выбрасываются), `.html` (скрипты вырезаются), Office через парсеры
  (`.xlsx/.xls/.docx/.pdf/.pptx`), архивы `.knwf/.zip`, картинки → в модель
  как изображения. Пределы размера — по СЫРОМУ файлу, читается уже
  очищенное → у `.ipynb`/`.html` предел отдельный (`MAX_RICH_BYTES`). Свои
  материалы, вернувшиеся в папке кандидата (`_is_our_material`),
  отсекаются. Дедуп по имени файла (`_Collector.is_new`). Непрочитанное →
  `skipped` → `decision_note` заказчику. Необязательный `GITHUB_TOKEN` в
  `config/.env` поднимает лимит GitHub API без токена (60/час) до 5000/час.
- **`net_bind.py`** — опциональная привязка исходящих HTTP (Anthropic,
  Telegram) к локальному IP через `PROXY_BIND_IP` в `.env`. Нужна только при
  прокси (`TG_PROXY`/`ANTHROPIC_PROXY`) + активном VPN одновременно.
  `PROXY_BIND_IP` = локальный IP физического адаптера ДО VPN (`ipconfig`).
  Пустая переменная = поведение как без модуля. Автоопределения нет.
- **`inbox_check.py`** / **`hiring_status.py`** — read-only отчёты по базе,
  каждая секция печатает SQL под собой. `hiring_status.py` — ЕДИНСТВЕННЫЙ
  источник истины «всё разобрано» (exit-код 0).
- **`gen_rating.py`** / **`dashboard.py`** — генерация `data/*.xlsx`
  (openpyxl) + HTML-дашборд воронки из тех же view (`funnel`,
  `candidate_history`).
- **`recruiter_card.py`** — карточка кандидата + рендер PDF резюме
  (reportlab/нативный PDF с HH) → Telegram HR-интервьюеру,
  `send_to_recruiter()`.
- **`transcribe.py`** — обёртка над faster_whisper (модель из
  `WHISPER_MODEL`) — распознавание записей интервью/голосовых.
- **`postinterview.py`** — сборка папки кандидата после интервью
  (`assemble_folder`): резюме+видео+транскрибация, ждёт ОТДЕЛЬНУЮ
  транскрибацию голосовых комментариев рекрутёра.
- **`fill_checklist.py`** — заполняет `Вакансии/Чек-лист_оценки.docx` по
  готовым данным (`fill_checklist()`), правила —
  `Вакансии/Регламент_заполнения_чек-листа.md`.
- **`hh_inbox.py`** — всё, что вываливается из автопилота воронки: `question`
  (кандидат написал последним), `self_decline` (снялся), `test_scored_stuck`
  (тест сдан, автооценка не отработала >`HH_INBOX_TEST_SCORE_STUCK_DAYS`, по
  умолчанию 2 дня). Сам ничего не шлёт: `scan()` → находки, `build_draft()` →
  черновик, показ+отправку делает `tg_bot2` через гейт «черновик → явное
  да». Показ — ТОЛЬКО по кнопке «📬 Переписка вне алгоритма». Контекст для
  черновика — ТОЛЬКО `FAQ_кандидату.md`, см. `.claude/rules/safety.md`. CLI:
  `python hh_inbox.py [role] [--draft]`.
- **`interview_scheduling.py`** — подбор+учёт времени ПЕРВИЧНОГО интервью +
  блок переноса УЖЕ назначенной встречи по инициативе рекрутёра. Полное
  поведение — `.claude/rules/telegram.md`.
- **`outreach.py`** — партии кандидатов на превск HR-интервьюеру (группа
  «МИУДОЛ: найм»). Отбор автоматический (все с оценённым тестом минус уже
  показанные), состав дашбордов рекрутёр задаёт списком ФИО. Полное
  поведение (файловый дубль, стоп-лист, сводка) — `.claude/rules/telegram.md`.
- **`group_watch.py`** — бот СЛУШАЕТ группу «МИУДОЛ: найм», отмечает, чьё
  резюме там появилось (`activity_log`, `group_seen`). Матчинг — по имени
  файла `resume_<neg_id>.pdf` или по ФИО (ЦЕЛЫЕ слова, НЕ подстрока). Чего
  Bot API не может и обходные пути — `.claude/rules/telegram.md`.
- **Внутренний контур импорта** (`internal_mail_poll.py` →
  `import_internal.py` → `internal_report.py`) — отдельная, полностью
  автономная параллельная воронка, НЕ пересекается с основной (HH).
  Кандидаты внутренней кадровой платформы приходят почтой: агент внутри
  закрытого контура (`internal_agent/collector.js`) дёргает REST API
  платформы, шлёт JSON/xlsx во внешний ящик; `internal_mail_poll.py`
  вычитывает вложения из `data/import/inbox/` (письмо → `processed`),
  `import_internal.py` апсертит в `internal_candidates`/
  `internal_import_batches` по `dedup_key`, `internal_report.py` — read-only
  отчёт. Эти кандидаты по воронке НЕ ведутся; совпадение с HH — мягкий флаг
  `possible_hh_resume_id` (`import_internal.find_possible_hh_duplicate`
  поверх `name_match.name_matches()`), решение о дубле — за человеком.
  Секреты — `IMPORT_MAIL_*` в `config/.env`, отдельно от
  `internal_agent/.env`. CLI: `python internal_mail_poll.py [--watch]`,
  `python import_internal.py файл.json [--watch]`, `python internal_report.py`.
- **`replay_dialogs.py`** — офлайн-прогон выгрузки переписки
  (`data/Переписка_<РОЛЬ>_<дата>.md`) через те же функции воронки
  (`parse_salary`, `hh_inbox`, автопилот) БЕЗ запросов к HH и отправок. 3
  read-only режима: сводка «что бы сделал автопилот»+находки `hh_inbox`,
  `--sim "Фамилия"` — пошаговая симуляция, `--salary` — `parse_salary` по
  всем сообщениям (эталон). «Дней прошло» у `hh_inbox` считается от
  сегодня — на старой выгрузке `test_overdue`/`salary_silence` почти всегда
  срабатывают; профиль в выгрузке не хранится, всем ставится 🟢.
- **`gen_dossier.py`** — досье кандидата после интервью (резюме+транскрипт+
  чек-лист) → HTML/PDF. Источник — ТОЛЬКО папка кандидата
  (`Вакансии/<роль>/Кандидаты/<ФИО>`).
- **`gen_batch_dashboard.py`** — батч-дашборд «кто сдал тестовое» (до
  интервью, тепловая карта+радар по 6 осям). Оси кешируются в
  `test_axes_assessment`, пересчитываются только при смене скоринга.
  Причина «не вошёл» — КОНКРЕТНАЯ (`_explain_unmatched`). По вакансиям без
  готового теста (`funnel.TEST_READY`, сейчас `arch`) — бот говорит СРАЗУ.
- **`gen_comparison_dashboard.py`** — сравнение кандидатов ПОСЛЕ интервью.
  В PDF обязательна секция «Чек-лист рекрутёра» с ДОСЛОВНЫМ комментарием.
  Рядом с рекомендацией ВСЕГДА печатается её источник (`rec_source`) —
  отметка рекрутёра или расчёт по баллам.
  ⚠ **Состав ОБОИХ дашбордов задаёт рекрутёр списком ФИО, автоотбора НЕТ**
  (с 26.07.2026): `build(role, names)` требует список, бот спрашивает «кого
  включить» вторым шагом (`_ask_report_names`). Вместе с автоотбором убран
  и ежедневный автотик батч-отчёта в 15:00 в группу (`BATCH_REPORT_TIME`,
  `_run_batch_report`) — фоновому тику список ФИО брать негде. Кто не
  попал в отчёт и почему — отдельным списком «Не вошли».
- **`name_match.py`** — сопоставление ФИО (ЦЕЛЫЕ слова, терпимо к
  падежам/инициалам) + разбор списка «1. Иванов 2. Петров». ЕДИНСТВЕННАЯ
  реализация на весь проект: `tg_bot2._word_matches` — обёртка над
  `word_matches()`, НЕ копия. Фамилии на -ский/-цкий сравниваются по ОСНОВЕ
  (условие «основа кончается на ск/цк» обязательно, иначе режет и личные
  имена). Проверено на 893 ФИО проекта. Подстрочный поиск ЗАПРЕЩЁН.
- **`pdf_export.py`** — HTML→PDF через headless Chromium (playwright).
  Первая установка: `python -m playwright install chromium`.
- **`group_cards.py`** / **`assessment_table.py`** — вспомогательные

## Схема БД (data/hiring.db, code/schema_sqlite.sql)

SQLite-адаптация серверной Postgres-схемы (TIMESTAMPTZ→TEXT ISO8601,
JSONB→TEXT, без GIN — полнотекст через `LOWER()` в Python). Таблицы:
`vacancies` (3 роли), `candidates` (резюме с HH, `raw` — полный JSON),
`applications` (1 отклик = 1 связка vacancy+resume, `employer_state`/
`score`/`category`/`scoring_json`/`decision`), `activity_log` (журнал всех
переходов/сообщений), `assessments` (⚠️ легаси, не заполняется),
`tg_scheduling` (стейт-машина Telegram — слот интервью, НЕ пересекается с
`employer_state`), `interview_slots` (встречи, записанные рекрутёром
вручную — второй источник слотов, формат `'YYYY-MM-DD HH:MM'`;
`cancelled_at` вместо удаления, `reported_at` — вошёл в сводку),
`interview_scores` (оценки чек-листа ПОСЛЕ интервью), `test_axes_assessment`
(кеш LLM-оценки по 6 осям), `outreach_tracking` (партии на превск),
`interview_reschedule_requests` (перенос уже назначенной встречи). View:
`funnel` (сводка роль×стадия), `candidate_history` (полная история),
`cross_applicants` (кто откликнулся больше чем на 1 роль).

Подробности и гочи схемы (двойная шкала `score`, кириллица в `LOWER()`) —
`.claude/rules/database.md`.
