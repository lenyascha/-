# Правило: автопилот воронки (funnel.py)

Читай перед правкой `funnel.py`, авто-отказов, порогов ЗП или кнопок
«🔒 Закрыть вакансию»/«🎉 Оффер». Структура модулей — `Документация/Архитектура.md`.
Хронология решений с датами — `Документация/Журнал_решений.md`.

## Стадии и потолки

`AUTO_FUNNEL=1` в `config/.env` включает автопилот для ВСЕХ ТРЁХ вакансий
(`FUNNEL_ROLES`), стадия восстанавливается из HH-чата на каждом тике:
профиль 🟢 → авто вопрос о ЗП → ответ (любая распознанная сумма) → авто
тестовое → детект сдачи → «готово к оценке».

Потолки ЗП: РАЦ 550к · РИИП 300к · Архитектор 500к (`funnel.CEILING`,
`_SALARY_CEILING` в tg_bot2) — ориентир для отчётов/рекрутёра, но **с
06.08.2026 НЕ решают, слать ли тестовое** (см. ниже).

- **Архитектор:** `TMPL_TEST_ARCH` — заглушка (`TEST_READY["arch"]=False`),
  автопилот НЕ шлёт тест, помечает «готов к тесту, но тест не составлен».
  Плюс стоп по гражданству (только РФ, поле `citizenship`).
- **РИИП/РАЦ:** тестовое готово, шлётся автоматически.

🟡-профиль не блокирует и не решает сам (эвристика намеренно грубая —
дальше ведёт LLM-скрининг резюме). Оценку СДАННОГО теста делает
`test_autoscore.py` автоматически на стадии `ready_to_score`, без
рекрутёра. Salary-gate перед тестом обязателен: факт «спросили и получили
число» — с 06.08.2026 НЕ сумма относительно потолка (см. ниже).
`FUNNEL_DRY_RUN=1` (по умолчанию) — только карточки «БЫ отправил»; боевой —
`FUNNEL_DRY_RUN=0`.

## Автоотказы (`funnel._AUTO_REJECT`) — реальные, не просто пометка

Все отправки — через `hh_core.move_to_reject` (`TMPL_REJECT_GENERIC`, без
причины кандидату), под контрактом 1 (`.claude/rules/hh-api.md`). После
отправки `applications.decision='reject'` выводит кандидата из выборки —
повторно не уйдёт. Тик, отправивший хоть один такой отказ, шлёт заказчику
отдельную сводку батчем — ЕДИНСТВЕННОЕ действие автопилота, о котором бот
пишет САМ без запроса (необратимое и внешне видимое кандидату).

1. **`reject_profile`** — правило-триаж 🔴 (`tg_bot2._triage`: нерелевантный
   титул или ЗП в резюме выше потолка роли).
2. **`reject_resume_score`** — LLM-категория резюме-скрининга
   (`applications.resume_category`) = «отказ» по регламенту роли:

   | Роль | Категория «отказ» | Примечание |
   |---|---|---|
   | rac | C | регламент: "C < 5.0 → отказ" |
   | piipl | C | регламент: "C < 5.0 → отказ" |
   | arch | D | шкала A/B/C/D — **C у Архитектора = «резерв/уточнить», НЕ отказ** |

   ⚠ Буква `C` значит РАЗНОЕ у разных ролей — не путать между ролями.
3. **`reject_citizenship`** (только Архитектор) — гражданство в резюме не
   РФ. Регламент вакансии требует автоотказ «даже при сильном профиле».
   Проверка идёт РАНЬШЕ резюме-скрининга в `next_action()`, на каждом тике
   заново — сработает на любой стадии, где кандидат оказался ДО введения
   правила, не только у новых откликов.
4. **`reject_vacancy_closed`** — пока у роли стоит `vacancies.closed_at`,
   возвращается любому кандидату без оффера, включая НОВЫЕ отклики после
   закрытия. Проверка стоит РАНЬШЕ «тест уже оценён» в `next_action()`.

**`offer_made`** — не отказ, а выход из воронки: `funnel.next_action`
проверяет `has_offer` ПЕРВЫМ, безусловно, раньше всех остальных проверок.

## ⚠ `reject_salary` — этого действия у автопилота НЕТ (с 06.08.2026)

Раньше ответ на salary-gate выше потолка роли останавливал кандидата
флагом «ручная проверка». Теперь `funnel.next_action` при ЛЮБОЙ
распознанной сумме (в т.ч. выше `CEILING`) возвращает `send_test` —
тестовое уходит всем, прошедшим резюме-скрининг и ответившим на вопрос про
ЗП хоть каким-то числом. ЗП выше потолка попадает в `reason` статуса
автопилота как пометка рекрутёру, НЕ повод остановить. Совместимость по
деньгам решается на собеседовании.

`TMPL_TEST_RAC/PIIPL/ARCH` несут ОДНУ И ТУ ЖЕ фразу про индивидуальное
обсуждение финансовых условий, одинаковую независимо от суммы — **не
делать её условной по сумме**: сам факт наличия/отсутствия фразы стал бы
сигналом кандидату, попал он в вилку или нет (тот же принцип, что у
`auto_reply.BODY_SALARY_NO_DISCLOSE`, см. `.claude/rules/safety.md`).

## Закрытие вакансии и оффер

- **«🔒 Закрыть вакансию»** — необратимо, роль НИКОГДА не угадывается
  автоматически, только явный выбор. Превью показывает 3 группы: кому
  уйдёт отказ (активные без оффера, кроме `interview`/`phone_interview`),
  кто с оффером (не трогаем), кто на финальном этапе (НЕ отказываем
  автоматически — решает рекрутёр). После подтверждения: архивация на HH
  (`hh_core.archive_vacancy` — обратного метода в HH API нет), список
  получателей перечитывается ЗАНОВО перед отправкой, каждому — ОТДЕЛЬНЫЙ
  `TMPL_REJECT_VACANCY_CLOSED` через `move_to_reject(..., force=True)`.
- **«🎉 Оффер»** — локальная пометка (`hiring_db.set_offer` →
  `applications.offer_note`), кандидату ничего не уходит, отклик не
  закрывается на HH. `offer_note` хранит комментарий, не булев флаг — UI не
  даёт оставить пустым.
- **Переоткрытие** — у HH нет метода «вернуть из архива», рекрутёр
  переоткрывает вручную на hh.ru, часовой тик
  (`tg_bot2._vacancy_reopen_tick`) сам снимает паузу: тот же `vacancy_id` →
  `hiring_db.reopen_vacancy`; новый `vacancy_id` с совпавшим заголовком
  (`_vacancy_titles_match`, нечёткое сравнение) → перепривязка
  (`hiring_db.rebind_vacancy_id`, тот же приём, что у РАЦ 01.07.2026).
  Заголовок совпал у нескольких публикаций → спросить рекрутёра явно, не
  гадать. Не совпал ни с чем — вакансия остаётся закрытой молча.
- Терминальное состояние HH-коллекции `discard_vacancy_closed`. Схема:
  `vacancies.closed_at`, `applications.offer_note`.
