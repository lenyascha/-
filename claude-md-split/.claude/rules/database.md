# Правило: база данных (hiring_db.py, data/hiring.db)

Читай перед SQL-запросами по кандидатам, фильтрами по тексту/городу или
отчётами «по тестовым». Полная схема таблиц/view —
`Документация/Архитектура.md`.

## ⚠️ `applications.score` хранит ДВЕ разные шкалы

Скоринг резюме (0–10) и оценка тестового (0–100) — в ОДНОЙ колонке.
Категория `A` встречается и с баллом 7.06 (резюме), и с 93 (тест).
Отличать — ТОЛЬКО `hh_core._is_test_score(score, scoring_json)`, не «на
глаз». Любой отчёт «по тестовым» (батч-дашборд, outreach-отбор, кнопки
«✅ Оценённые тестовые»/«📦 Батч-дашборд») ОБЯЗАН фильтровать шкалу этой
функцией — иначе в отчёт про тест попадает скоринг резюме с подписью
«Итоговый балл теста: 7.06». `funnel.avg_score` как средний балл смысла не
имеет; `ORDER BY score DESC` смешивает шкалы. (Разделение на 2 колонки —
открытая задача, не решена.)

## ⚠️ `LOWER()` в SQLite не работает с кириллицей

`LOWER('Москва')` вернёт БЕЗ ИЗМЕНЕНИЙ. Любой сырой SQL-фильтр по русскому
тексту (`WHERE city = LOWER(...)`, `LIKE`) молча возвращает 0 строк или
всё подряд. Это баг движка SQLite, не промпта — **промпт-инструкциям
(«не забудь привести к нижнему регистру») тут доверять бесполезно**, фикс
только на уровне SQL/Python в `hiring_db.py`. Для text-to-SQL слоя
(`run_readonly_query`, генерируемый LLM для свободных вопросов) это
означает: сгенерированный SQL с `LOWER()`/`LIKE` по кириллическим полям
будет молча неверным, а не упадёт с ошибкой — при добавлении новых
свободных вопросов проверять на реальном кириллическом вводе, не только на
латинице.

## Поиск кандидата по имени — НЕ подстрока

`full_name_lower` — регистр приводится на стороне Python при
синхронизации, поиск идёт по этому полю целиком или по явным границам
слов. **Подстрочный поиск запрещён**: 81% базы однажды осталась без
пересчитанного `full_name_lower` (`sync_hh.py` не переобрабатывает старые
записи при повторном синке), точный поиск проваливался в фолбэк «по
первым 4 буквам где угодно в строке» и подставил не того кандидата
(«Гулидов» → «Рогулин», журнал инцидентов п.7). Та же функция используется
в «отказ»/«пригласи» — риск реальный, не косметический.

Единственная реализация сопоставления ФИО на весь проект —
`name_match.word_matches()` (`tg_bot2._word_matches` — тонкая обёртка, НЕ
копия). Не заводить вторую копию логики сравнения ФИО в другом модуле:
одна копия с исправленным правилом и вторая забытая = кандидат находится в
одной команде и не находится в другой (было в проекте до 26.07.2026).

## Таблицы с двумя источниками одного факта — приоритет ручного

Везде, где встреча/отправка/статус может появиться и автоматически
(бот/автопилот), и вручную (рекрутёр записал) — ручная запись
приоритетнее, а сводки/отчёты обязаны читать ОБА источника, не только
автоматический (см. `.claude/rules/telegram.md` про `tg_scheduling` vs
`interview_slots`). Если добавляешь новую таблицу с той же природой
(автомат + ручной ввод одного и того же факта) — сразу закладывай этот
приоритет и двойное чтение, а не после того, как обнаружится, что половина
записей не попадает в сводку.
