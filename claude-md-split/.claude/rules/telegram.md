# Правило: Telegram-бот (tg_bot2.py и связанные модули)

Читай перед правкой клавиатуры, `outreach.py`, `interview_scheduling.py`,
`group_watch.py` или `hh_inbox.py`. Структура — `Документация/Архитектура.md`.

## ⚠ Кнопки — обычный текст, без callback_data

Диспетчер матчит ТЕКСТ нажатой кнопки: точным совпадением по
`_CANDIDATE_BUTTONS`, иначе — regex-правилами `ADM_*` в
`classify_admin_text`. **Любая точечная правка текста кнопки (в
`_MAIN_KEYBOARD`/`_ROOT_KEYBOARD`/`_SUBMENUS`) обязана сопровождаться
проверкой** — хотя бы прогоном `classify_admin_text(text, use_llm=False)`
на новый текст. Иначе поломка тихая: кнопка нажимается, ответ приходит,
просто не тот (реальный случай — 3 кнопки разошлись с диспетчером
одновременно, журнал инцидентов п.27).

Клавиатура сгруппирована (с 03.08.2026): корневая на 6 категорий
(Кандидаты/Тестовые/Аналитика/Собеседование/Превск/Система,
`_ROOT_KEYBOARD`) → подменю + «⬅️ Назад» (`_SUBMENUS`,
`_submenu_keyboard`). Текст КАТЕГОРИИ никогда не участвует в
диспетчеризации действия, только текст итоговой кнопки внутри подменю — та
же ловушка актуальна и там.

## Два режима бота

1. **Командный** (`ADMIN_CHAT_ID`) — свободный текст →
   `llm_client.classify_admin_text` → `admin_dispatch`. Голосовые тоже
   команды (`transcribe()` → текст → тот же путь), КРОМЕ стадии
   `await_voice` пост-интервью пайплайна (там голосовое = оценка).
   Свободные вопросы к базе → text-to-SQL (`write_readonly_sql` →
   `run_readonly_query` → `summarize_query_result`), ответ текстом без
   показа SQL; действия («отказать всем из Москвы») — только через гейт
   «черновик → явное подтверждение».
2. **Стейт-машина кандидата** (`tg_scheduling`) — ПЕРВИЧНОЕ интервью
   (15–20 мин, HR-интервьюер), бот согласует время сам.

## ⚠ Два РАЗНЫХ источника встреч — не путать

- `tg_scheduling.confirmed_slot` — ПЕРВИЧНОЕ интервью, бот согласовал сам с
  кандидатом на HH-канале.
- `interview_slots` — ВТОРОЕ, ФИНАЛЬНОЕ собеседование с Плаксиным Д.А.
  (заказчик). HR-интервьюер списывается с кандидатом ЛИЧНО в Telegram,
  время сам — бот НЕ участвует, в `tg_scheduling` такие слоты не
  появляются НИКОГДА. Вводится словами: `_record_interview_slots`
  (`_parse_slot_when`+`_parse_slot_entries`, формат «Иванов Иван — 30.07
  15:00», повтор = перенос). Два входа: команда в любой момент
  (`ADM_SET_SLOT` → `set_interview_slot`) и кнопка «➕ Добавить кандидата»
  на сверке-чекбоксе. Различать формы: «назначен/договорились» = факт (в
  базу), «назначь/предложи» = просьба боту написать (`propose_slot`).
  Отказ/самоотвод снимают слот (`hiring_db.cancel_interview_slot`).
- Вечерний свод и сводка по превску читают ОБА источника (с 06.08.2026) —
  ручная запись приоритетнее bot-slot.
- Перенос УЖЕ назначенной встречи по инициативе РЕКРУТЁРА (форс-мажор,
  кнопка «🔁 Перенести встречу») работает одинаково для обеих встреч —
  своя таблица `interview_reschedule_requests`, свой тик
  (`reschedule_tick`, вызывается из `tg_bot2._hh_tick` НЕЗАВИСИМО от
  `INTERVIEW_AUTOPILOT_ENABLED` — это прямое продолжение действия,
  которое рекрутёр уже подтвердил явным «✅ Отправить кандидату», не
  автопилот). Поток: сетка часов → подтверждение →
  `TMPL_INTERVIEW_RESCHEDULE_BY_RECRUITER` в HH-чат → если нет ответа
  >`RESCHEDULE_REMIND_AFTER_DAYS` (2 дня), одно напоминание
  (`TMPL_INTERVIEW_RESCHEDULE_REMIND`). Не путать с переносом по
  инициативе КАНДИДАТА (та логика внутри автопилота `tg_scheduling`,
  другой код). Пока по `negotiation_id` открыта запись в
  `interview_reschedule_requests`, `next_interview_action` возвращает
  `held` и не трогает — иначе ответ кандидата попал бы в обе логики
  одновременно.

## Фоновые тики

`_scheduler_loop()`: `_sync_tick` (раз в `SYNC_INTERVAL_SEC`),
`_funnel_tick` (только при `AUTO_FUNNEL=1`), `_refresh_token_if_due` (раз в
5 дней), вечерний свод по `EVENING_SUMMARY_TIME`. **Тики НИЧЕГО не
показывают по своей инициативе**, кроме сбоев и раздела «🔔 Уведомления»
(новые отклики + реальный автоотказ автопилота — необратимые/видимые
события). Всё остальное — по кнопке, никогда пушем: то, что перехватывает
следующий ввод админа (гейт «да/нет»), нельзя показывать без спроса
(журнал инцидентов п.16).

**`_acquire_singleton_lock()`** (`data/.tg_bot2.lock`) — не даёт второй
копии бота. Запуск/остановка ТОЛЬКО через `run_bot.bat`/
`run_bot_hidden.vbs`/`stop_bot.ps1`, НЕ ручным `Stop-Process`.

## hh_inbox — pull, не push

3 повода позвать рекрутёра: `question`, `self_decline`, `test_scored_stuck`.
Показ — ТОЛЬКО по кнопке «📬 Переписка вне алгоритма», разбор по одной
карточке, в любой момент «выход»/«пропустить». Дедуп по решению
(«да»/«нет»), не по показу. Автонапоминания кандидату из этого модуля
УБРАНЫ целиком 10.08.2026 (см. `Документация/Журнал_решений.md`) — не
добавлять их снова без явного запроса заказчика.

## outreach.py — партии на превск

Отбор автоматический (все с оценённым тестом минус уже показанные), состав
ОБОИХ дашбордов (батч + сравнение) рекрутёр задаёт списком ФИО (с
26.07.2026, автоотбора нет). «Уже показанным» считается: запись в
`outreach_tracking`, `tg_card_sent`, `group_seen`, назначенный/проведённый
собес — **и файловый дубль** `Вакансии/<роль>/Превск/<ФИО>.pdf`
(`hiring_db.save_outreach_resume_copy`/`outreach_folder_has_resume`) как
резервная копия того же факта, переживающая рассинхрон БД. **Показом
считается ТОЛЬКО отправка в НАСТОЯЩИЙ чат группы** (`real_group_chat`) —
пока `TG_CHAT_MAP`/`TG_CHAT_ID` ведут в личку `ADMIN_CHAT_ID`, всё это
тест-режим, кандидаты остаются новыми. Ручной стоп-лист —
`outreach_excluded` («не включай Иванова» — `ADM_OUTREACH_EXCLUDE` →
`_exclude_from_outreach`; «верни Иванова» — `ADM_OUTREACH_INCLUDE`),
проверяется ПЕРВЫМ, независимо от тест-режима.

## group_watch.py — чего Bot API не может

Не читает историю ДО добавления бота в группу, не видит сообщения других
ботов, не получает сообщения при включённом privacy mode (если бот не
администратор группы). Обходные пути без настроек Telegram: переслать
карточку боту в личку (`_handle_admin_forward`) или сказать «Иванова уже
показывали в группе» (`ADM_MARK_SHOWN`). Матчинг ФИО — ЦЕЛЫЕ слова, НЕ
подстрока (журнал инцидентов п.7).
