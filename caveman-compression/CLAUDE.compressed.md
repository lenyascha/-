## ⚠ Несколько чатов Claude Code одновременно — координация БЕЗ отдельной просьбы

Если в папке параллельно работают несколько чатов (в т.ч. над РАЗНЫМИ,
не связанными задачами) — не ждать, пока пользователь опишет процесс.
Определять самой, координироваться через файлы на диске, не через пересказ.
Правило постоянное, как и правило про артефакт выше.

**Перед любой задачей** (правка кода — не только когда явно сказано «работаем
параллельно») — молча, без вопроса:
1. Прочитать `.tasks/` — путь ВСЕГДА абсолютный,
   `C:\Users\internet\Desktop\HRochka\.tasks\`, даже если сессия работает в
   worktree другой задачи (см. п.4).
2. Прочитать `git branch --list "task/*"` и `git worktree list`.
3. Самой придумать слаг задачи из формулировки пользователя (коротко,
   латиницей, kebab-case) — формат/имя не спрашивать.
4. Если файлы/модули задачи не пересекаются ни с одной активной записью
   `.tasks/` — завести ветку `task/<slug>` от `master` (или
   `task/<slug>/<часть>` + отдельный `git worktree` в
   `C:\Users\internet\Desktop\HRochka-worktrees\<slug>__<часть>`, если явно
   параллельная работа над ОДНОЙ задачей несколькими чатами), создать
   `.tasks/<slug>.md` по шаблону `.tasks/_TEMPLATE.md`, начать работу — без
   остановки на подтверждение, это не рискованное действие.
5. Если пересечение ЕСТЬ — с чужой активной задачей или со списком «вечно
   эксклюзивных» действий ниже — остановиться, спросить пользователя, не
   решать самой.

`.tasks/*.md` **не версионируется git** (в `.gitignore`) — живое состояние
координации между чатами сейчас, не история проекта (историю несут ветки и
коммиты). Один файл на задачу, не общий список — чтобы реестр сам не стал
источником конфликтов при параллельной записи. Тот же приём уже есть в проекте:
`data/.tg_bot2.lock` — локальный, не версионируемый файл для той же цели (не
пускать два процесса одновременно), см. карту модулей, `_acquire_singleton_lock()`.
Тот же принцип, расширенный с одного бота на произвольные задачи.

**Вечно эксклюзивные действия** — сколько бы задач ни шло параллельно, выполняет
только один чат в момент и только с подтверждением пользователя (правила не
новые, здесь просто собраны вместе):
- реальные (не dry-run) действия на HH — отказ/приглашение/тестовое/сообщение;
- `config/.env` и обновление HH-токена (`refresh_token.py`);
- старт/остановка `tg_bot2.py`;
- публикация `Документация/Техническая_документация.html` через Artifact.

**Мерж частей одной задачи** — тоже не параллельно: под-ветки вливаются в ветку
задачи по одной (автоматически, без вопроса — это ещё не `master`, откат дёшев),
конфликты разруливаются на этом шаге, не в процессе работы; при реальном
конфликте (не fast-forward) — не гадать, какая сторона верная, показать
пользователю обе версии, спросить. Финальный мерж ветки задачи В `MASTER` — уже
НЕ автоматически, только с подтверждением: своего PR/ревью в проекте нет, это
единственная точка проверки перед тем, как задача войдёт в основную линию.
После мержа всех частей и самой ветки в `master` — закрытие задачи автоматическое,
без отдельного вопроса (подтверждение уже получено на самом мердже): удаляются
`.tasks/<slug>.md`, ветка `task/<slug>` (`git branch -d` — сработает только если
правда влита, заодно и проверка) и её `git worktree`, если был отдельный. Раньше
ветки/worktree после мерджа не убирались — за пару недель накопилось 5 смерженных,
но висящих веток и папок-worktree (обнаружено, вручную снесено 04.08.2026). Теперь
это часть закрытия задачи, не отдельное поручение.

## Установка и перенос на другой ПК

Тестов/линтера/сборки нет — набор автономных Python-скриптов, не пакет. Установка
одной командой — **`setup.bat` в корне** (двойной клик): ставит пакеты, докачивает
Chromium для playwright, создаёт недостающие папки, накатывает схему
`data/hiring.db`, переопределяет `PROXY_BIND_IP` под эту машину, живыми запросами
проверяет HH-токен, оба Telegram-токена и ключ Anthropic. Отчёт по-русски,
«блокеры / оговорки»; exit-код 0 = можно запускать `run_bot.bat`.

Он же — диагностика при «что-то не работает»:
```bash
py code/setup_check.py                      # только проверить
py code/setup_check.py --install --write    # то же, что setup.bat
py code/setup_check.py --offline            # без сетевых проверок
```
`--write` чинит только безопасное (папки, схема БД, `PROXY_BIND_IP`,
`config/.env.example`). **Секреты не придумывает и не трогает.**

**Обязательно копировать при переносе** (остальное — код, в git/архиве):
- `config/.env` — единственное невосстановимое автоматически (секретный файл, не
  пересылать открытыми каналами);
- `data/hiring.db` — вся история кандидатов и решений;
- `Вакансии/**` — регламенты, FAQ, папки кандидатов (досье и дашборд сравнения
  собираются ТОЛЬКО из файлов папки кандидата, база тут не поможет).

После копирования: `setup.bat` → поправить, что назовёт блокером → `run_bot.bat`.
Единственная машинозависимая переменная — `PROXY_BIND_IP` (локальный IP
физического адаптера, см. `net_bind.py`); `setup_check.py` определяет и прописывает
сам, руками лезть больше не нужно.

Ручная установка, если `setup.bat` не подходит:
```bash
pip install -r code/requirements.txt   # requests, openpyxl, reportlab, pypdf, playwright, python-docx, docx2pdf
python -m playwright install chromium   # отдельный шаг: pip сам браузер не ставит
pip install faster_whisper              # только если нужна транскрибация
```
(`docx2pdf` требует установленный MS Word — им рендерится PDF чек-листа после
интервью.) Все скрипты запускаются из `code/`, сами читают `../config/.env` и
открывают `../data/hiring.db` — пути от файла модуля, поэтому проект переносится в
любую папку без правок.

## Карта модулей (code/)

Слоями, от HH API до вывода наверх:

- **`hh_core.py`** — тонкий клиент HH API (`get_headers`, `get_resume`,
  `change_collection`, `send_chat_message`) + ВСЕ контракты воронки поверх
  (`move_to_assessment/reject/consider/interview`, `record_test_score`, preflight
  `_preflight_reject`/`_preflight_assessment`, `_salary_gate_passed`). ЕДИНСТВЕННОЕ
  место смены состояния отклика на HH — не дублировать `change_collection` в
  других модулях. `move_with_message()` — обход бага HH API (пустое сообщение при
  смене коллекции, журнал ошибок п.3).
- **`hiring_db.py`** — весь доступ к `data/hiring.db` (sqlite3, без ORM).
  `ensure_schema()` накатывает `schema_sqlite.sql` при первом обращении. Поиск
  кандидата по имени — `LOWER()` на стороне Python (`full_name_lower`), НЕ FTS и
  НЕ SQL `LOWER()`/`LIKE` — **встроенный `LOWER()` SQLite не работает с
  кириллицей** (`LOWER('Москва')` вернёт без изменений) → сырой SQL-фильтр по
  русскому тексту молча возвращает 0 строк или всё подряд (журнал ошибок п.6).
  `run_readonly_query()` — read-only SQL от LLM для свободных вопросов к базе
  (см. `llm_client.write_readonly_sql`/`summarize_query_result` и раздел про
  свободные вопросы ниже); фильтр на запрещённые ключевые слова (не
  `SELECT`/`WITH` → отказ). `hh_core.py` вызывает функции модуля для записи
  side-effects после каждого действия на HH — `applications`/`activity_log`
  обновляются рядом с изменением на HH, не отдельным синком.
- **`sync_hh.py`** — забирает новые отклики/резюме с HH →
  `hiring_db.upsert_candidate_from_hh`/`upsert_application` → база.
  Однонаправленно HH→БД; обратной синхронизации нет, все исходящие — только
  через `hh_core.py`.
- **`templates.py`** — все шаблоны сообщений кандидатам (`TMPL_*`) + фикс.
  подпись `SIG`. ЕДИНСТВЕННОЕ место текста сообщений — не собирать текст inline
  в других модулях.
- **`funnel.py`** — чистая логика автопилота воронки (`next_action`, `run_step`):
  по стадии+профилю решает следующий шаг (резюме-скрининг → salary-gate → тест →
  детект сдачи). К HH (`hh_core.move_to_reject`/`resend_message`) обращается
  ТОЛЬКО из `run_step` при `dry_run=False` (вызывается из `tg_bot2.py`). С
  31.07.2026 два сигнала резюме-скрининга шлют РЕАЛЬНЫЙ автоотказ на HH:
  правило-триаж 🔴 (`reject_profile`) и LLM-категория = «отказ» по регламенту
  роли (`reject_resume_score`, `RESUME_REJECT_CATEGORY = {"rac": "C", "piipl":
  "C", "arch": "D"}` — ⚠ буква та же "C", смысл разный: РАЦ/РИИП C=отказ,
  Архитектор C=резерв, там отказ только D). Цель — не пропускать явно негодных
  дальше до ручной проверки. ⚠ Отказ по гражданству (`reject_citizenship`,
  только Архитектор) ДО 06.08.2026 под это правило не попадал (был только
  флагом) — с этой даты тоже реальный автоотказ (см. врезку про гражданство в
  «Автопилот воронки» ниже). С 07.08.2026 добавилось 4-е действие —
  `reject_vacancy_closed` (роль закрыта кнопкой «🔒 Закрыть вакансию», не
  авто-детект как первые три) + пара `offer_made` (пометка «🎉 Оффер» выводит
  кандидата из воронки ЦЕЛИКОМ, не только защищает от этого отказа) — см.
  «Закрытие вакансии и оффер» ниже. ⚠ С 06.08.2026 действия `reject_salary` у
  автопилота НЕТ ВООБЩЕ — тестовое уходит всем, кто прошёл резюме-скрининг и
  назвал на salary-gate любую сумму, даже выше потолка; деньги обсуждаются на
  собеседовании, не на этом шаге. Подробности — «Автопилот воронки» ниже.
- **`tg_bot2.py`** (самый крупный модуль, ~1500 строк) — двухрежимный Telegram-бот,
  длинный поллинг (`get_updates`/`run()`):
  1. **Командный режим** (`ADMIN_CHAT_ID`) — разбор свободного текста через
     `llm_client.classify_admin_text`, диспетчер `admin_dispatch` (карточки
     кандидатов, рейтинг, дашборд, слоты интервью). Голосовые — тоже команды:
     `transcribe()` (faster_whisper) → текст → тот же путь; ИСКЛЮЧЕНИЕ — этап
     `await_voice` пост-интервью пайплайна: там голосовое = сама оценка
     кандидата, не команда. Пайплайн стартует «собеседование с Ивановым
     завершилось» (`interview_done_start` — запись→транскрибация→голосовое→
     чек-лист) либо, если транскрибация встречи уже готова (обрыв на голосовом,
     журнал ошибок п.23), продолжается с шага оценки командой «чек-лист по
     Иванову» (`checklist_from_transcript_start`, без повторной транскрибации).
     **Свободные вопросы к базе** (не «отказ»/«пригласи»/«список кандидатов») →
     text-to-SQL: `llm_client.write_readonly_sql` → `hiring_db.run_readonly_query`
     → `llm_client.summarize_query_result` — ответ текстом, SQL не показывается.
     Работает и для действий («отказать всем из Москвы») — но только через гейт
     «черновик → явное подтверждение», не в обход preflight-проверок
     `hh_core.py`.
  2. **Стейт-машина кандидата** (`tg_scheduling`) — приглашение → слот Телемоста
     → подтверждение, через `apply_transition`/`_handle_candidate`. Это
     **ПЕРВИЧНОЕ интервью** (15–20 мин, HR-интервьюер) — время бот согласует сам,
     кандидату вручную не пишет никто.
     ⚠ **Второй, РУЧНОЙ источник встреч — `interview_slots`, ДРУГОЙ этап: ВТОРОЕ,
     ФИНАЛЬНОЕ собеседование с Плаксиным Д.А.** (заказчик, решение). На него
     HR-интервьюер по итогам первички списывается с каждым кандидатом ЛИЧНО в
     Telegram, время сам — бот не участвует, автоматизировать нечем, в
     `tg_scheduling` такие слоты не появляются НИКОГДА. «Кто на какое время» —
     вводится словами: `_record_interview_slots` (`_parse_slot_when` +
     `_parse_slot_entries`, формат «Иванов Иван — 30.07 15:00», несколько строк
     сразу, повтор = перенос). Два входа: команда в любой момент (`ADM_SET_SLOT`
     → `set_interview_slot`) и кнопка «➕ Добавить кандидата» на сверке-чекбоксе
     перед «🧾 Сводкой по превску» и вечерним сводом
     (`_stage_bot_slots_review`/`_stage_evening_slots_review`, общий обработчик
     `_handle_slots_add`, см. п.6 ниже). Спрашивать ДО построения сводки: после
     неё висит черновик отправки в группу, перехватывающий ввод — дописать нельзя
     (журнал ошибок п.16). Писать в `tg_scheduling.confirmed_slot` НЕЛЬЗЯ: там
     состояние переписки кандидата С БОТОМ, запись без диалога сделала бы

## Схема БД (data/hiring.db, code/schema_sqlite.sql)

SQLite-адаптация серверной Postgres-схемы (TIMESTAMPTZ→TEXT ISO8601, JSONB→TEXT,
без GIN — полнотекст через `LOWER()` в Python). Таблицы: `vacancies` (3 роли),
`candidates` (резюме с HH, `raw` — полный JSON), `applications` (1 отклик = 1
связка vacancy+resume, `employer_state`/`score`/`category`/`scoring_json`/
`decision` — состояние воронки на HH), `activity_log` (журнал всех переходов/
сообщений), `assessments` (тестовые — ⚠️ легаси, ничем не заполняется),
`tg_scheduling` (стейт-машина Telegram-бота — слот интервью, НЕ пересекается с
`employer_state`), `interview_slots` (встречи, о которых рекрутёр договорился
ЛИЧНО мимо бота, записал руками — второй источник слотов рядом с
`tg_scheduling.confirmed_slot`, формат тот же `'YYYY-MM-DD HH:MM'`;
`cancelled_at` вместо удаления, `reported_at` — вошёл в сводку по превску),
`interview_scores` (оценки чек-листа ПОСЛЕ интервью, источник дашборда
сравнения), `test_axes_assessment` (кеш LLM-оценки по 6 осям для батч-дашборда),
`outreach_tracking` (партии на превск: отправлен→закрыт→вошёл в сводку),
`interview_reschedule_requests` (перенос уже назначенной встречи по инициативе
рекрутёра, см. `interview_scheduling.py` выше — пока по `negotiation_id` есть
строка, ответ кандидата НЕ подтверждается автопилотом сам, уходит рекрутёру на
явное да/нет; строка удаляется по завершении эпизода, отдельного статуса нет).
View: `funnel` (сводка роль×стадия), `candidate_history` (полная история по всем
вакансиям), `cross_applicants` (кто откликнулся больше чем на 1 роль).

⚠️ **`applications.score` хранит ДВЕ разные шкалы:** скоринг резюме (0–10) и
оценка тестового (0–100). Отличать — `hh_core._is_test_score(score,
scoring_json)`, НЕ «на глаз»: категория `A` встречается и с 7.06 (резюме), и с
93 (тест). Все отчёты «по тестовым» ОБЯЗАНЫ фильтровать шкалу:
`gen_batch_dashboard.build`, `outreach.split_pool`, `tg_bot2._scored_tests_for_role`
(общий фильтр для «✅ Оценённые тестовые»/«📦 Батч-дашборд») — иначе в отчёт
про тест попадает скоринг резюме с подписью «Итоговый балл теста: 7.06».
Поэтому `funnel.avg_score` как средний балл смысла не имеет, а
`ORDER BY score DESC` смешивает шкалы. Разделение на 2 колонки — открытая
задача.

```python
hh_core.move_to_assessment(neg_id, templates.TMPL_TEST_RAC.format(name="Иван"),
                            vacancy_id=134764878, resume_id="...",
                            score=8.1, category="A", scoring_json={...})

# Записать оценку СДАННОГО тестового (без смены коллекции на HH) — ЕДИНАЯ точка.
# Сама шлёт карточку кандидата заказчику в бот №2 (admin-чат) — не пиши скоринг
# напрямую через hiring_db.set_scoring, иначе карточка не уйдёт. blocks: 5 блоков
# рубрики (depth/hypotheses/prioritization/visualization/management) + final(0..100).
hh_core.record_test_score(neg_id, blocks={"depth":18,"hypotheses":18,
                          "prioritization":18,"visualization":17,"management":18,"final":89},
                          category="A", decision_note="...стоп-факторы, что подготовлено...")
```

## ⛔ Контракты в коде (машина не даст нарушить — не капризы, уроки прошлых ошибок)

1. **`move_to_reject(...)` блокируется**, если кандидат уже в `interview`/
   `phone_interview` или `decision='interview'`, или за 7 дней был переход на
   след. этап. Обход — `force=True` + `decision_note` ≥10 символов. Причина:
   реальный случай — отказ ушёл ДО назначенной встречи, пришлось извиняться.
2. **`move_to_assessment(...)` требует полный `scoring_json`** по 6 критериям
   (`data, aiml, team, industry, lang, soft` + `final`) — формула в
   `Вакансии/<роль>/Регламент_найма.md`. Без него — исключение.
3. **`move_to_assessment(...)` требует пройденный salary-gate** — в HH-чате
   должен быть наш вопрос про мин. ЗП (`TMPL_SALARY_GATE_*`) и ответ
   кандидата с цифрой. Причина: без фильтра тестовые уходили кандидатам,
   отваливавшимся потом на несовместимой ЗП — недели впустую.
   `_salary_gate_passed()` — ТРИ состояния: `True`/`False`/`None` («не смог
   проверить — нет связи с HH»). `None` блокирует так же, как `False` (раньше
   при сетевом сбое возвращался `True`, и таймаут молча снимал контракт).
4. **`hiring_status.py` — ЕДИНСТВЕННОЕ основание для «всё сделано».** Пока
   exit-код не 0 — работа не закончена, говорить обратное нельзя (проверяемо:
   под каждой секцией SQL).
5. **Разбор суммы ЗП — ТОЛЬКО `hh_core.parse_salary()`**, одна функция на весь
   проект (`funnel._parse_salary`/`tg_bot2._detect_salary` — обёртки). Свой
   разбор не писать: прежняя версия брала первое число в сообщении, «Готов с
   1 июля, зарплата 600» читала как 1 000₽ — кандидат проходил под потолок,
   автоматом получал тестовое. `None` из неё = «НЕ РАСПОЗНАЛ», не «не
   назвал»: такой ответ уходит рекрутёру (`funnel`→`salary_unclear`), не
   пропускается по воронке.
6. **Контекст для сообщений кандидату — ТОЛЬКО
   `Вакансии/<роль>/FAQ_кандидату.md`.** `Регламент_найма.md` (потолок ЗП,
   возрастные отсечки, стоп-факторы, гражданство) в модель, пишущую текст
   кандидату, НЕ передаётся НИКОГДА. Плюс детерминированный фильтр
   `llm_client.reply_is_safe()` поверх промпта: текст кандидата идёт в модель
   = потенциальная инъекция, на «мы попросили модель не говорить» полагаться
   нельзя.

## ✅ Чек-лист внешней отправки (кандидату / HR-интервьюеру) — проверять каждый раз

1. **Подпись — фиксированная, `templates.SIG`: «А. Терещенков».** Имя
   владельца HH-аккаунта (`GET /me`) — не выдумывать другое, не подставлять
   своё: кандидаты знают это имя с прошлой переписки, смена на середине
   диалога — красный флаг кандидату и накладка нам.
2. **Получатель сверен:** `neg_id`↔ФИО↔`resume_id` по базе. Один человек =
   одно сообщение.
3. **Текст — сначала превью**, реальная отправка только после явного решения
   (`confirmed=False` сначала везде, где есть параметр).
4. **НИКОГДА не озвучивать кандидату вилку ЗП работодателя**, не давать
   причин отказа (только `TMPL_REJECT_GENERIC`).
5. **После отправки — перепроверить доставку** (перечитать
   `/negotiations/{neg_id}/messages`) — у HH глюки с пустыми системными
   сообщениями, `move_with_message()` уже защищает, но факт доставки стоит
   перепроверять на важных сообщениях.

## HH-токен — как обновлять, чтобы не протухал

Токен живёт ~14 дней с выпуска, потом любой запрос → 403 `bad_authorization`,
**воронка встаёт целиком** — стадия кандидата не хранится, каждый тик
восстанавливает её из переписки HH.

⚠️ **«Обновлять профилактически» НЕЛЬЗЯ — HH не разрешает.** На обновление
живого токена отвечает `400 invalid_grant / "token not expired"`, новую пару
не даёт. Прежний совет «запускай раз в 5-7 дней» физически не работал: каждый
запуск падал с ошибкой. Единственный рабочий порядок — **сначала проверить,
потом обновлять**:
```bash
py code/refresh_token.py     # сам проверит /me; живой токен = exit 0, ничего не трогает
```
То же делает бот при КАЖДОМ запуске (`tg_bot2._refresh_token_if_due(force=True)`):
проверяет `/me`, обновляет только если токен реально мёртв. Не вышло
обновиться — пишет в admin-чат громко: воронка стоит, нужен вход через
браузер.

**Почему токен всё-таки теряется насовсем.** HH гасит старый `refresh_token`
в момент выдачи нового. Если процесс упадёт между ответом HH и записью в
`config/.env` — новый токен негде взять, старый уже мёртв, HH отвечает
`token has already been refreshed` (реальный случай 28.07.2026). Поэтому
`refresh_token.py` пишет новую пару СНАЧАЛА в `data/.hh_token_backup.json`,
потом в `.env`; при следующем запуске пробует токен из резервной копии, если
тот в `.env` не сработал.

Не помогло — нужен новый вход через браузер, порядок в
`ИНСТРУКЦИЯ_для_новичка.pdf`, раздел «Если совсем протухло».

## Ежедневный ритуал
Начало дня: `sync_hh.py` → `inbox_check.py`. По ходу дня — разбор секций.
Конец дня/сессии: `hiring_status.py` — exit 0 = можно отчитаться, что всё
разобрано.

**Авто-режим (с 14.07.2026):** держать запущенным `python tg_bot2.py` (под
VPN) — запуск/остановка ТОЛЬКО через `run_bot.bat` (видимое окно) или
`run_bot_hidden.vbs` (без окна)/`stop_bot.ps1`, НЕ вручную `Stop-Process` по
имени (журнал ошибок пп.8-9). Бот сам раз в час (`SYNC_INTERVAL_SEC`) тянет
HH→базу (`sync_hh.sync_all()`), шлёт заказчику в admin-чат карточку на
КАЖДЫЙ новый отклик (кандидат впервые в базе; >8 за раз — сводкой), раз в 5
дней освежает токен, при сбое синка/токена — громко пишет в admin-чат (не
молчит). Ручной `sync_hh.py` никуда не делся. ВАЖНО: пока бот/ноутбук
выключен — тянуть неоткуда, «автоматика» живёт только пока крутится процесс.
Все read-пути (команды бота, карточки, `hiring_status`) читают локальную
базу — пустая/устаревшая → сначала синк (авто или ручной).

**Автопилот воронки (`funnel.py`, флаг `AUTO_FUNNEL=1` в `config/.env`):**
ведёт кандидатов ВСЕХ ТРЁХ вакансий (`FUNNEL_ROLES`), восстанавливая стадию
из HH-чата на каждом тике: профиль 🟢 → авто вопрос о ЗП → ответ (любая
распознанная сумма) → авто тестовое → детект сдачи → «готово к оценке».
Потолки ЗП свои: РАЦ 550к · РИИП 300к · Архитектор 500к
(`funnel.CEILING`/`_SALARY_CEILING` в tg_bot2) — используются
отчётами/дашбордами и ориентиром рекрутёру в статусе автопилота, но **с
06.08.2026 НЕ решают, слать ли тестовое** (см. врезку про `reject_salary`
ниже). Различия по вакансиям:
- **Архитектор:** тестовое `TMPL_TEST_ARCH` — заглушка
  (`TEST_READY["arch"]=False`), автопилот НЕ шлёт, помечает «готов к тесту,
  но тест не составлен» (открытая задача). Плюс стоп по **гражданству**
  (только РФ, поле `citizenship`) — с 06.08.2026 реальный автоотказ (см.
  врезку ниже), не просто флаг.
- **РИИП/РАЦ:** тестовое готово, шлётся автоматически.

Границы намеренные: 🟡 — не блокирует, но и не решает сам, эвристика
намеренно грубая (дальше ведёт более надёжный сигнал — LLM-скрининг резюме).
Оценку СДАННОГО теста тоже делает не человек — `test_autoscore.py` (модель
по полному тексту `Регламент_найма.md` роли, единая точка записи
`hh_core.record_test_score`) запускается автоматически из
`tg_bot2._funnel_tick` на отметке `ready_to_score`, без рекрутёра; сама
`funnel.py` оценку не считает, только доводит кандидата до отметки (дальше
факт «есть неоценённый тест» подхватывает `_funnel_tick` — это НЕ «оценка
вручную», формулировка про «Claude в сессии» устарела). Salary-gate перед
тестом обязателен (auto-шаг, журнал ошибок п.2) — обязателен сам факт
«спросили и получили число», НЕ сумма относительно потолка (разошлось
06.08.2026, см. врезку ниже: до этой даты проверка была двойной). Отправки
идемпотентны (по чату). `FUNNEL_DRY_RUN=1` (по умолчанию) — только карточки
«БЫ отправил», реальных сообщений нет; боевой — `FUNNEL_DRY_RUN=0`.

⚠ **С 31.07.2026 (резюме-скрининг) и 06.08.2026 (гражданство) отказы шлются
автоматически, не только помечаются** (оба раза — решение заказчика: явные
стоп-факторы не должны занимать место в воронке до ручной проверки). 3
сигнала, всё через `funnel._AUTO_REJECT`:
- **`reject_profile`** — правило-триаж 🔴 (`tg_bot2._triage`: нерелевантный
  титул или ЗП в резюме выше потолка роли).
- **`reject_resume_score`** — LLM-скрининг резюме (`resume_autoscore.py`,
  `applications.resume_category`) попал в категорию = «отказ» по регламенту
  роли: **C** у РАЦ/РИИП (регламент: "C < 5.0 → отказ"), **D** у Архитектора
  (там шкала A/B/C/D — C = "резерв/уточнить", НЕ отказ; путать буквы между
  ролями НЕЛЬЗЯ).
- **`reject_citizenship`** (только Архитектор, добавлен 06.08.2026) —
  гражданство в резюме не РФ. Регламент (`Вакансии/Архитектор
  данных/Регламент_найма.md`, раздел «Гражданство») требует автоотказ «даже
  при сильном профиле» — до 06.08.2026 код только помечал флагом. Проверка
  идёт РАНЬШЕ резюме-скрининга в `next_action()` (сразу после «тест уже
  оценён»), на каждом тике заново — сработает на любой стадии, где кандидат
  оказался ДО этого дня, не только у новых откликов.

Все 3 отправки — через `hh_core.move_to_reject` (`TMPL_REJECT_GENERIC`, без
причины кандидату) из `funnel.run_step` при `FUNNEL_DRY_RUN=0`, под
контрактом 1 (защита от отказа на защищённой стадии). После отправки
`applications.decision='reject'` выводит кандидата из выборки автопилота —
повторно не уйдёт. Тик, отправивший хоть один такой отказ, шлёт заказчику
отдельную сводку (батчем) — ЕДИНСТВЕННОЕ действие автопилота, о котором бот
пишет САМ без запроса (в отличие от salary-gate/теста — видно только по «📡
Статус автопилота»): необратимое и внешне видимое кандидату действие.

На момент введения правила резюме-скрининга (31.07.2026) в базе уже было 14
кандидатов с резюме-категорией «отказ», висевших без движения (11
Архитектор/D, 3 РАЦ/C) — по решению заказчика правило применяется и к ним:
на первом тике после деплоя тоже получат реальный отказ. Для гражданства
(06.08.2026) backlog проверен отдельно — на дату введения активных
кандидатов-архитекторов с гражданством не РФ не было (0 из 21 активных),
немедленных отказов при включении не произошло.

⚠ **С 06.08.2026 действия `reject_salary` у автопилота НЕТ ВООБЩЕ** (решение
заказчика, тот же аудит, что и правило про резюме-скрининг, для более
позднего шага). До этой даты ответ на salary-gate выше потолка роли
останавливал кандидата флагом «ручная проверка» — тестовое не уходило, пока
рекрутёр не решал вручную. Теперь `funnel.next_action` при ЛЮБОЙ
распознанной сумме (в т.ч. выше `CEILING`) возвращает `send_test` —
тестовое уходит всем, прошедшим резюме-скрининг и ответившим на вопрос про
ЗП хоть каким-то числом; ЗП выше потолка попадает в `reason` статуса
автопилота как пометка рекрутёру («📡 Статус автопилота»), не повод
остановить. Совместимость по деньгам решается на собеседовании, не на этом
шаге. `TMPL_TEST_RAC/PIIPL/ARCH` поэтому несут ОДНУ И ТУ ЖЕ фразу про
индивидуальное обсуждение финансовых условий — одинаковую независимо от
суммы: показывай её только выше-потолочным — сам факт наличия/отсутствия
стал бы сигналом, попал кандидат в вилку (тот же принцип, что
`auto_reply.BODY_SALARY_NO_DISCLOSE` на «попадаю ли я в вилку», см.
`Документация/План_автономной_воронки.md`, §2). То же решение автоматически
убрало ручную эскалацию по теме `salary`/`never_money` в `auto_reply.py` для
«сумма выше потолка» — физически не может возникнуть, раз `next_action` для
неё больше не отдаёт отдельное действие.

**Закрытие вакансии и оффер** (кнопки «🔒 Закрыть вакансию»/«🎉 Оффер»,
добавлено 07.08.2026): ручная остановка приёма по одной роли + защита
конкретного кандидата от последствий этой остановки — 2 разных, но связанных
механизма.

- **«🔒 Закрыть вакансию»** — необратимое действие, роль НИКОГДА не
  угадывается автоматически (даже при одной активной) — только явный выбор.
  Превью (`_build_vacancy_close_preview`, `hiring_db.vacancy_active_applications`)
  — 3 группы: кому уйдёт отказ (все активные без «🎉 Оффер», кроме
  `interview`/`phone_interview`), кто с оффером (не трогаем), кто на
  финальном этапе (`interview`/`phone_interview` — НЕ отказываем
  автоматически, решает рекрутёр сам). После подтверждения: вакансия
  архивируется на HH (`hh_core.archive_vacancy` — обратного метода в HH API
  нет, снять с архива можно только вручную на hh.ru), список получателей
  перечитывается ЗАНОВО прямо перед отправкой (не из черновика — пока
  рекрутёр читал превью, кому-то могли поставить оффер/сменить стадию),
  каждому — ОТДЕЛЬНЫЙ шаблон `TMPL_REJECT_VACANCY_CLOSED` (не общий
  `TMPL_REJECT_GENERIC` — причина отказа не секретна, вакансия правда
  закрыта) через `hh_core.move_to_reject(..., force=True)` — `force`, т.к.
  рассылка целиком уже осознанное решение рекрутёра, контракт 1 здесь не
  переспрашивает по каждому отдельно.
  Дальше это НЕ разовое действие: пока у роли стоит `vacancies.closed_at`,
  `funnel.next_action` на КАЖДОМ тике возвращает `reject_vacancy_closed`
  любому кандидату без оффера — 4-е действие в `funnel._AUTO_REJECT` (см.
  врезку про резюме-скрининг/гражданство выше) — значит и НОВЫЕ отклики
  после закрытия тоже получат автоотказ сами. Проверка стоит РАНЬШЕ «тест уже
  оценён» в `next_action()` — иначе кандидат с оценённым тестом ушёл бы в
  `scored` (no-op) вместо реального отказа.
- **«🎉 Оффер»** — чисто локальная пометка (`hiring_db.set_offer` →
  `applications.offer_note`), кандидату ничего не уходит, отклик не
  закрывается на HH. Смысл — застолбить БЫСТРЕЕ, чем `sync_hh` подтянет
  родной `employer_state=offer/hired` с HH (раз в час), вывести кандидата из
  воронки ЦЕЛИКОМ: `funnel.next_action` проверяет `has_offer` ПЕРВЫМ,
  безусловно, раньше всех проверок (действие `offer_made`) — без этого
  автопилот мог успеть отправить вопрос про ЗП/тестовое, а по Архитектору
  (`TEST_READY["arch"]=False`) вообще ничто своё его бы не остановило.
  `offer_note` хранит комментарий, не булев флаг — пустая строка и NULL
  неотличимы, UI не даёт оставить пустым, подставляет «без комментария».
- **Переоткрытие** — у HH нет метода «вернуть из архива» (проверено по
